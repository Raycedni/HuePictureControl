## Decisions Made
- Reordered the highlight roll-off (tone-map) step to run in the native BT.2020 gamut before the BT.2020->BT.709 primaries matrix, rather than after as the plan's literal step list specified. The plan explicitly granted discretion over "the exact curve" as long as the neutral/hue invariants held; running the matrix first caused a legitimate highlight-bright saturated orange sample (PQ code value near the top of the curve, representing >10x SDR reference white) to drive the matrix's negative off-diagonal terms below zero in the non-dominant channels, which then clipped to exact zero — collapsing the intended orange hue toward a near-primary red with G=B=0. Tone-mapping first compresses the dominant channel into a comparable range before the matrix runs, which preserves the intended R>G>B ordering.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Reordered tone-map step to avoid hue-rotation on saturated highlight samples**
- **Found during:** Task 1 (writing the known-value orange-hue test from the plan's own `<behavior>` spec)
- **Issue:** Following the plan's literal step order (matrix -> clip -> tone-map) on the plan's own example input `[220,130,40]` produced `R=251,G=0,B=0` — failing the plan's own `R>G>B` strict-inequality assertion (`G` and `B` both clipped to exactly 0). This is precisely the hue-rotation defect the feature exists to fix.
- **Fix:** Applied the extended-Reinhard tone-map in the native BT.2020 gamut before the BT.2020->BT.709 matrix (steps 4 and 6 swapped relative to the plan's numbered list). Verified numerically against all four invariants (neutral gray stays neutral, orange becomes `R>G>B`, black stays black, bright white stays valid+near-neutral) before updating the implementation.
- **Files modified:** `Backend/services/color_math.py`
- **Verification:** All 6 new `TestHdr10ToSrgb` tests pass; full `test_color_math.py` suite (53 tests) green.
