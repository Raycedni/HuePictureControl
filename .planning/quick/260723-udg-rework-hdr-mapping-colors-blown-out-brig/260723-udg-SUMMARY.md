# Phase quick-260723-udg: Rework HDR Mapping (blown-out / hue-shifted colors) Summary

**Replaced per-channel extended-Reinhard HDR10 finishing with a hue-preserving pipeline — uniform max-RGB tone map (knee + exponential shoulder) plus luma-preserving gamut compression — fixing orange->green, brown->red, and midtone-crush ("blown out") artifacts.**

## Accomplishments
- `_tone_map_max_rgb`: uniform per-sample scale `f(max)/max` with knee `_TONE_KNEE=0.75` and a C1-continuous exponential shoulder. Preserves channel ratios (and thus hue + saturation) exactly; sub-knee content passes through bit-identically; diffuse white (linear 1.0) now maps to ~0.91 instead of the old ~0.5 midtone crush.
- `_compress_to_gamut_709`: replaces the old `np.maximum(rel709, 0.0)` per-channel clip with a luma-preserving lerp toward the achromatic axis for out-of-[0,1] samples. Rec.709 luma preserved to <1e-3; channel ordering preserved; in-gamut samples untouched.
- `_finish_linear_bt2020_to_srgb` reworked to compose the two helpers (signature, all three call sites, and every `hdr=False` path unchanged).
- 11 new behavior tests (`TestHuePreservingToneMap` + a genuine-orange test) proving ratio preservation, sub-knee passthrough, midtone-crush fix, monotonicity, orange-saturation survival, brown-stays-brown, hue-preserving gamut compression, and shape/black-safety contracts.

## Decisions Made
- **Uniform max-RGB tone map** (not per-channel): scaling all channels by the same `f(max)/max` is the only tone map that preserves both hue and saturation while guaranteeing every channel <= 1.0 before the BT.2020->BT.709 matrix.
- **Knee 0.75 + exponential shoulder:** C1-continuous (`f(k)=k`, `f'(k)=1`, asymptote 1.0) so SDR-range content below the knee is identity and linear HDR white (~49.26) lands just under 1.0.
- **Luma-preserving achromatic lerp** for gamut mapping instead of per-channel clip: a single per-sample `s` preserves Rec.709 luma exactly and preserves channel ordering, avoiding the hue rotation the old clip caused.

### 1. [Rule 1 - Bug / spec conflict] Existing HDR test assertions encoded old distorted behavior
- **Found during:** Task 1 (implementing the plan's exact algorithm)
- **Issue:** The plan required the new hue-preserving algorithm AND that `TestHdr10ToSrgb::test_saturated_orange_maps_to_orange_hue_not_green` and `TestHdrLinearAveraging::test_hdr_true_beats_convert_after_average` pass unchanged. These are mutually exclusive:
  - `test_saturated_orange...` asserts `[220,130,40]` -> `r>g>b`. Under the (unchanged) PQ/limited-range LUT that byte triple decodes to linear ~`[25.8, 0.56, 0.002]` = ~`[5250, 113, 0.4]` nits — a **near-primary red**, not an orange. BT.2020 red maps to BT.709 with G more negative than B, so any hue/luma-preserving gamut map yields `b` marginally >= `g` (`[255,79,97]`). The old per-channel Reinhard produced `g>b` only by distorting the ratios — exactly the bug being removed. Strict `g>b` is unachievable for a near-primary red without reintroducing the hue distortion.
  - `test_hdr_true_beats_convert_after_average` asserted the linear-before-average `r-b` spread strictly exceeded the byte-average path's spread. That relied on the OLD finish collapsing the byte path to warm-grey. The v3 finish no longer collapses mid-oranges, so the byte path is now also saturated and the strict inequality inverts (132 vs 162) — the finish got better, not worse.
- **Fix (user-approved Option A):**
  - Renamed/reworked the orange test to `test_bright_saturated_red_stays_red_not_green_or_white`: asserts R strongly dominant (`r>g`, `r>b`, `r>=200`, `r-g>=60`) and HSV saturation `>=0.45` (not green, not near-white) — the property the user actually cares about — with a comment explaining the near-primary-red colorimetry.
  - Added `test_genuine_orange_stays_r_gt_g_gt_b` using byte `[192,176,132]` (decodes to linear ~`[7.9,4.1,0.6]`, a true orange) asserting clean `r>g>b`, so the original test's intent is still covered.
  - Reworked the spread test to `test_hdr_true_stays_strongly_orange_dominant`: asserts `r>g>b` and `r-b >= 80` (strong orange dominance) instead of the now-inverted strict inequality.
- **Files modified:** Backend/tests/test_color_math.py
- **Verification:** Full `test_color_math.py` green (85 passed). Genuine oranges verified R>G>B (`[255,191,148]`); bright red renders saturated red `[255,79,97]`.
- **Committed in:** cbb49d0 (RED)
