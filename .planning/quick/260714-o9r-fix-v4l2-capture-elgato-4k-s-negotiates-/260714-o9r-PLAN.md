Root cause confirmed empirically: VIDIOC_S_FMT reports success AND `v4l2-ctl --get-fmt-video` afterward confirms `'MJPG'`, but VIDIOC_DQBUF delivers raw YUYV (no FFD8 SOI marker, chroma bytes near 0x80). `bytesused` is always exactly 614400 = 640*480*2 (raw YUYV frame size), never a variable compressed JPEG size. The driver lies about the negotiated format, so format-readback alone is NOT reliable — content detection is required. The device genuinely supports YUYV at 640x480 per `v4l2-ctl --list-formats-ext`.

Do NOT touch `Backend/services/color_math.py` or the `hdr=True` path — they operate on the decoded BGR frame from `get_frame()` and are already correct regardless of wire format.

     `frame = cv2.cvtColor(yuyv, cv2.COLOR_YUV2BGR_YUYV)`,
     `ok, buf = cv2.imencode(".jpg", frame, [cv2.IMWRITE_JPEG_QUALITY, 85])` (re-encode so the preview WS still gets valid JPEG — mirrors capture_dshow.py:131). If not `ok` return `None`. Return `(frame, buf.tobytes())`.

5. Rewrite the decode section of `_reader_loop()` (lines ~318-329) to call the helper:

Keep the existing lock, `_last_frame_time`, `_frame_seq`, and `_new_frame_event.set()` wiring intact. Do NOT add per-frame format sniffing outside the helper's cached `self._decode_yuyv` check.

Keep the MJPEG path behavior byte-for-byte for real-MJPEG devices (imdecode + raw jpeg_data stored). This is an additive fallback, not a replacement.
