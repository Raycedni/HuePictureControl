# Phase 19.1: WLED Segment Sync - Context

**Gathered:** 2026-05-14
**Status:** Ready for planning

<domain>
## Phase Boundary

Replace Phase 19's paint-managed `wled_channels` table as channel source-of-truth with the WLED device's own `seg[]` array fetched from `/json/state`. The downstream assignment + streaming pipeline (region → assignment → orientation → coordinator → wled_streamer) keeps its shape — only the channel origin and the table that stores it change. Phase 19's strip-paint UI is locked into a read-only segment visualizer (no mutate verbs). The four manual UAT items (V1–V4) deferred from Phase 19 are re-mapped to the segment-driven model and executed before close.

Explicitly out of scope: WLED write-back (pushing seg edits from HPC back to the device), WebSocket subscription to WLED state pushes, per-device default orientation, polygon-path LED mapping, undo/redo, HA control endpoints (Phase 18), painter-to-config-tool repurposing.

</domain>

<decisions>
## Implementation Decisions

### Sync trigger
- **D-01:** Segments are pulled from each WLED device via **HTTP GET `/json/state`** using the existing `httpx` pattern from `Backend/services/wled_client.py`. No new transport library. No WebSocket. No periodic polling.
- **D-02:** Refresh fires on three triggers and **no others**:
  - Device registration (one extra GET to `/json/state` immediately after the existing `/json/info` fetch in the registration handler — both calls in the same coroutine, so registration fails atomically if either fails)
  - User clicks the **per-device "Refresh" button** in the WLED tab header
  - Backend startup re-hydration is NOT triggered automatically; the cache survives restart via the new `wled_seg_cache` table (see D-12)
- **D-03:** Refresh button placement: **per-device header** inside each device's section of `SettingsPanel` / `SettingsPage`. One button per device, no global "refresh all". Mirrors the granularity of Phase 17's per-device scan/enable controls.
- **D-04:** Offline behavior on refresh: **keep last-known segs in `wled_seg_cache`**, show a "stale, last refreshed X ago" indicator on the device header in the WLED tab + LightPanel. Streaming continues against cached segs — same posture as Phase 17 for offline devices. The exact stale-badge UI is Claude's discretion (small inline timestamp + warning icon is the obvious shape).
- **D-05:** No refresh during a live streaming session is auto-fired by HPC. The user can still click the button while streaming; behavior is the same (cache update, assignments reconciled, frame loop picks up the new ranges on the next tick).

### Strip painter fate
- **D-06:** `WledStripPainter.tsx` becomes a **read-only segment visualizer**. The Konva strip canvas, per-LED scaling, `channelColor(index)` zone fills, and ResizeObserver fit-to-width all stay. **Removed:** paint gesture (mousedown/move/up), boundary drag handles, the `paintReducer` state machine entirely. The component still renders one strip per device per D-15 from Phase 19; it just no longer accepts pointer input that mutates state.
- **D-07:** `WledChannelSidebar.tsx` becomes a **read-only metadata panel** when a strip zone is clicked. Shows: WLED-side segment name (D-08 resolution), seg index, `start_led`–`stop_led` range, length. Removed: name input, start/end inputs, Delete button. Selection wiring stays so the sidebar still reacts to zone clicks.
- **D-08:** Display name resolution per segment: **WLED `n` field if present, else `"Segment {seg_index}"`**. The same string is used in the strip's inline label, the LightPanel WLED chip row, the region orientation popover's channel list, and `WledChannelSidebar`. One helper function (e.g. `Frontend/src/utils/wled-segment.ts → segmentName(seg)`) owns the resolution.
- **D-09:** Channel-color palette identity (`channelColor(index)`) **stays anchored to seg_index per device**, not to the dropped `wled_channels.id`. This preserves the V2 chip-vs-strip color parity test by keying both surfaces off the same integer (the seg_index). The frontend palette helper at `Frontend/src/utils/wled-palette.ts` keeps its signature; callers pass `seg_index` where they used to pass `channel_index_within_device`.
- **D-10:** The Phase 19 channel-CRUD endpoints + service code are **hard-removed** as dead code (not deprecated). Specifically removed:
  - `Backend/routers/wled.py`: `POST/PUT/DELETE /api/wled/devices/{id}/channels...` + `PUT /api/wled/channels/{id}/boundary` + the `list_channels` endpoint as written (replaced by `GET /api/wled/devices/{id}/segments` — see D-17)
  - `Backend/services/wled_channels.py`: `create_channel_with_split`, `resize_boundary`, `delete_channel_with_cascade`, `_next_channel_name`. The whole file is deleted unless a residual helper is genuinely shared. The `wled_devices.next_channel_n` migration is also retired (column survives in DB after migration, but no code reads/writes it).
  - `Frontend/src/components/Settings/wled-paint-reducer.ts` — deleted.
  - `Backend/tests/test_wled_channels.py` and the channel-CRUD/boundary cases in `test_wled_router.py` are deleted.

### Identity & continuity
- **D-11:** Stable identity for an HPC-tracked WLED channel is the composite **(device_id, seg_index)**. The `wled_channels.id` UUID is gone. WLED `seg.id` is positional and matches `seg_index` exactly when reading `/json/state` — we trust that ordering. User-driven reordering on the WLED app is treated as deliberate reconfiguration, not as a name-survival problem to solve.
- **D-12:** Schema: drop `wled_channels` entirely; introduce **`wled_seg_cache`** with PK `(device_id, seg_index)` and columns `(start_led, stop_led, name, refreshed_at)`. Mirrors the last known `/json/state seg[]` for the device, written only by the refresh handler.
- **D-13:** Assignment table is rewritten: `wled_light_assignments(region_id, wled_device_id, seg_index, entertainment_config_id, orientation)`, PK `(region_id, wled_device_id, seg_index, entertainment_config_id)`. The `orientation` column from Phase 19 D-16 carries forward unchanged (same enum, same default `'auto'`, same per-region constraint enforced via the PATCH endpoint).
- **D-14:** Reconciliation rules on every refresh (single transaction):
  1. DELETE all rows in `wled_seg_cache` WHERE `device_id = ?` (wipe-and-rewrite per D-19).
  2. INSERT one row per element of the device's seg[].
  3. DELETE any `wled_light_assignments` rows where `(wled_device_id, seg_index)` no longer exists in `wled_seg_cache` for that device. Hard-delete. No orphan flag, no "broken" badge. (D-15)
  4. Range changes on still-existing `seg_index` values are absorbed silently — the new `start_led`/`stop_led` are written to the cache, the assignment row keeps pointing at `(device_id, seg_index)`, and the next coordinator frame plan uses the new range. (D-16)
- **D-15:** When a refresh removes segments (count shrinks, indices no longer exist), the assignment rows pointing at the missing indices are **hard-deleted in the same transaction as the cache write**. Region's WLED arrow in popover/canvas just disappears on the next render. No toast, no badge, no orphan state.
- **D-16:** Range change on an existing `seg_index` is treated as **metadata-only**. The cached `start_led`/`stop_led` update silently; the assignment row is untouched; the frame loop reads the new range on next tick. No user-visible notification (the strip visually re-renders with the new range, which is the notification).
- **D-17:** New endpoint: **`POST /api/wled/devices/{device_id}/segments/refresh`** — triggers a `/json/state` fetch, runs the full reconciliation transaction (D-14), returns the post-refresh segment list + the count of assignments dropped (so the frontend can surface it in the strip header).
- **D-18:** New endpoint: **`GET /api/wled/devices/{device_id}/segments`** — reads `wled_seg_cache` for the device. No device contact. Used by the frontend to render the strip after a page reload without forcing a refresh.

### Schema & data lifecycle
- **D-19:** Cache write strategy: **DELETE-then-INSERT per device in one transaction**. Simplest semantics — the cache mirrors `/json/state seg[]` exactly after every refresh. No upsert dance, no per-index diff, no intermediate state visible to readers (SQLite serializes writes).
- **D-20:** Upgrade path: **drop and recreate**. `init_db` issues `DROP TABLE IF EXISTS wled_channels` and `DROP TABLE IF EXISTS wled_light_assignments` (gated by a one-shot guard, e.g. a `schema_version` row or a presence-check on the new `wled_seg_cache` table) on first init after upgrade, then recreates `wled_light_assignments` with the new shape (D-13) and creates `wled_seg_cache`. Rationale: single-user, single-machine tool; no production data to preserve; Phase 19 just shipped. Re-registering devices + re-assigning regions is the expected upgrade cost.
- **D-21:** Orientation lifecycle: `orientation` continues to live as a column on `wled_light_assignments`. When the last assignment for a `(region_id, entertainment_config_id)` pair is deleted by the reconcile cascade (D-15), the orientation value is gone too — there is no separate orientation table. Acceptable because orientation has no meaning without an assignment to apply it to. (No new "preserve orientation across re-wires" UX is in scope; deferred.)
- **D-22:** Coordinator gradient contract from Phase 17 D-05 / Phase 19 D-22 (`{region_id: gradient_array}`) **stays unchanged**. The SQL in `streaming_coordinator._build_region_plan` is rewritten to join `wled_light_assignments` against `wled_seg_cache` (instead of `wled_channels`) on `(wled_device_id, seg_index)`. `N_region = max(stop_led - start_led + 1 for every assigned seg)` continues. `sub_sample_gradient(orientation=)` is called the same way per region.

### Re-mapped manual UAT (V1–V4)
- **D-23:** All four deferred manual UATs from Phase 19 (V1 live LED color, V2 chip-vs-strip color parity, V3 boundary handle, V4 full-stack restart) are **re-mapped** to the segment-driven model and executed once before phase close. Captured in `19.1-VALIDATION.md` during planning. Specifically:
  - **V1 (live LED color)** — unchanged in intent. Test path: configure a segment on the WLED device (via WLED app or its web UI), register the device in HPC (D-02 triggers initial fetch), open the WLED tab, drag the segment chip onto a canvas region, start streaming, point the region at a known color. Physical strip updates at ~60 Hz match the region color.
  - **V2 (chip-vs-strip color parity)** — same test, now keyed on `seg_index` (D-09). Five segments configured on WLED; the strip's zone fill for index N matches the LightPanel chip for index N. Both call `channelColor(seg_index)`.
  - **V3 (boundary handle)** — **OBSOLETE** as written (no painter mutation). **Replaced** with a new V3' test: configure two adjacent segments on the WLED app, view them in HPC, then on the WLED side change the boundary between them (e.g., reduce seg 0 length, grow seg 1), click the per-device Refresh button in HPC, and verify the strip in HPC re-renders with the new ranges. This exercises D-02 + D-14 + D-16 end-to-end through a live browser + live device.
  - **V4 (full-stack restart)** — same intent. Register a device, refresh once to populate `wled_seg_cache`, make a region assignment, change an orientation, restart the backend, reload the browser. The strip layout (from cached segs), assignment, and orientation all survive. No device contact required to render the strip post-restart, since the cache is on disk.

### Claude's Discretion
- Exact placement and styling of the per-device "Refresh" button + stale-badge indicator inside the WLED tab header (e.g. icon-only button, ghost variant, badge as tooltip vs. inline text).
- Cache row shape: whether to also store WLED-side `grp`/`spc` for future use, or only the four fields enumerated in D-12. Smallest workable set is preferred.
- Whether the upgrade guard for D-20 is a `schema_version` table, a `PRAGMA user_version` bump, or a presence-check on `wled_seg_cache`. Simplest workable check wins.
- Frontend behavior when a refresh response reports `dropped_assignments > 0` — silent UI refetch is fine; a small toast like "Removed N stale assignments" is acceptable if the planner judges it valuable.
- Whether `Frontend/src/components/Settings/WledStripPainter.tsx` is renamed (e.g. `WledStripView.tsx`) when mutation verbs are removed, or kept under the old name for diff minimalism. Either is acceptable.
- Whether `wled_devices.next_channel_n` migration column is dropped in this phase or left as harmless dead schema for a future cleanup. Either is acceptable.
- The exact Pydantic models for the new refresh + list-segments endpoints — follow the `WledApiError` and request/response shape conventions already in `Backend/routers/wled.py`.
- Coordinator SQL rewrite: whether to JOIN `wled_seg_cache` directly in `_build_region_plan` or read it once via a helper function. Whichever keeps the SQL readable; the join is preferred for SQL parallelism with the Hue path.
- Test strategy for the removed Konva paint interactions in `e2e/wled-paint.spec.ts` — replace the paint test with a "segment list renders from refresh" test; the boundary-resize test becomes the V3' refresh roundtrip.

<specifics>
## Specific Ideas

- `fetch_wled_state(ip)` returns `list[dict]` with one dict per element of WLED's `state.seg`, normalized to `{seg_index: int, start: int, stop: int, name: str | None}`. Defensive-parse missing fields the same way `fetch_wled_info` does. (Some firmwares omit `n`; some put `name` somewhere else — handle gracefully.)
- `wled_seg_cache` table shape:
  ```sql
  CREATE TABLE IF NOT EXISTS wled_seg_cache (
      device_id TEXT NOT NULL,
      seg_index INTEGER NOT NULL,
      start_led INTEGER NOT NULL,
      stop_led INTEGER NOT NULL,
      name TEXT,
      refreshed_at TEXT NOT NULL,
      PRIMARY KEY (device_id, seg_index),
      FOREIGN KEY (device_id) REFERENCES wled_devices(id) ON DELETE CASCADE
  )
  ```
- Rewritten `wled_light_assignments` shape:
  ```sql
  CREATE TABLE IF NOT EXISTS wled_light_assignments (
      region_id TEXT NOT NULL,
      wled_device_id TEXT NOT NULL,
      seg_index INTEGER NOT NULL,
      entertainment_config_id TEXT NOT NULL,
      orientation TEXT NOT NULL DEFAULT 'auto',
      PRIMARY KEY (region_id, wled_device_id, seg_index, entertainment_config_id)
  )
  ```
- Reconciliation transaction body (pseudo-Python):
  ```python
  async with db.transaction():  # implicit via aiosqlite
      await db.execute("DELETE FROM wled_seg_cache WHERE device_id = ?", (device_id,))
      await db.executemany(
          "INSERT INTO wled_seg_cache (device_id, seg_index, start_led, stop_led, name, refreshed_at) "
          "VALUES (?, ?, ?, ?, ?, ?)",
          rows,
      )
      cursor = await db.execute(
          "DELETE FROM wled_light_assignments "
          "WHERE wled_device_id = ? AND seg_index NOT IN ("
          "    SELECT seg_index FROM wled_seg_cache WHERE device_id = ?"
          ")",
          (device_id, device_id),
      )
      dropped = cursor.rowcount
      await db.commit()
  return {"segments": rows, "dropped_assignments": dropped}
  ```
- Drag payload shape (D-13 supersede):
  ```ts
  // LightPanel.tsx onDragStart
  e.dataTransfer.setData("wledDeviceId", device.id);
  e.dataTransfer.setData("seg_index", String(seg.seg_index));
  e.dataTransfer.setData("wledSegName", segmentName(seg));
  e.dataTransfer.setData("entertainmentConfigId", configId);
  ```
- `EditorCanvas.handleDrop` discriminator branches on presence of `wledDeviceId` (rather than `wledChannelId`).
- Stale-badge UI: small inline `text-muted-foreground` text below the device name, e.g. "synced 12s ago" → "stale (3m ago)" once the cache age exceeds a threshold (Claude's discretion, ~60s feels right). No live timer; a `setInterval(1000)` to update the relative string when the WLED tab is mounted is fine.
- `data-testid` plan: `wled-refresh-button-{device_id}` on the button, `wled-stale-badge-{device_id}` on the badge, `wled-seg-{device_id}-{seg_index}` on each strip zone + LightPanel row.

<deferred>
## Deferred Ideas

- **WLED write-back from HPC** — pushing seg edits (rename, resize, add, remove) from HPC to the device via `POST /json/state`. The strip painter could become a config tool, not just a consumer. Out of scope for 19.1; potential future phase.
- **WebSocket push subscription** — replace the manual refresh button with `ws://{ip}/ws` to mirror device-side seg edits in near-real-time. Higher fidelity, higher complexity (lifecycle, reconnect). Deferred until manual refresh proves insufficient.
- **Periodic background refresh / debounced auto-refresh on tab focus** — could reduce "stale" friction. Deferred; trivial to add later if the manual model proves annoying.
- **Orientation preservation across re-wires** — promote `orientation` to a per-region table so the axis choice survives losing all assignments. Deferred until users hit it.
- **Stale-badge threshold + visual treatment polish** — pick a sensible default (~60s feels right) now; revisit if it's annoying in practice.
- **WLED `n` (name) writeback** — letting the user rename a segment in HPC and have it sync to the device. Falls under "WLED write-back" above; deferred.
- **WLED `grp`/`spc` (grouping/spacing) handling** — currently ignored. If a user uses grp/spc on the WLED side, HPC will treat the segment range as raw start..stop; the streaming color of grouped LEDs will look fine because WLED renders the average to the grouped pixels.
