## Sync trigger

### Q1 — When should HPC refresh segments from the WLED device?

| Option | Description | Selected |
|--------|-------------|----------|
| Manual refresh button | User-triggered button in the WLED tab. Predictable, zero background traffic. | ✓ |
| On tab open + manual refresh | Auto-refresh on WLED tab mount plus manual. | |
| On tab open + on streaming start + manual | Refresh whenever it matters: tab mount, stream start, manual. | |
| WebSocket subscribe (push) | Subscribe to `ws://{ip}/ws` for real-time updates. | |

**User's choice:** Manual refresh button
**Notes:** Simplest, lowest network footprint. Predictable for a single-user LAN tool.

### Q2 — Where should the refresh button live?

| Option | Description | Selected |
|--------|-------------|----------|
| Per-device header in WLED tab | One refresh button per device row. | ✓ |
| Single global 'Refresh all' button | One button hits all devices in parallel. | |
| Both per-device and 'Refresh all' | Per-device buttons + shortcut. | |

**User's choice:** Per-device header in WLED tab
**Notes:** Granular control matches Phase 17's per-device scan/enable model.

### Q3 — What if the device is unreachable when refresh fires?

| Option | Description | Selected |
|--------|-------------|----------|
| Keep last known segs, show stale indicator | Cached segs stay visible; badge tells the user. | ✓ |
| Clear segs + show error | Wipe the cache; UI shows empty/error state. | |
| Keep segs, block streaming until refresh succeeds | Conservative: streaming blocked on transient outage. | |

**User's choice:** Keep last known segs, show stale indicator
**Notes:** Consistent with Phase 17's optimistic-cache posture for offline WLED devices.

### Q4 — Does HPC also fetch segs at WLED device registration time?

| Option | Description | Selected |
|--------|-------------|----------|
| Yes — fetch /json/info + /json/state in one go | Two GETs at registration; device immediately ready. | ✓ |
| No — only fetch info, segs come from first manual refresh | Cheaper registration, requires explicit user step. | |

**User's choice:** Yes — fetch /json/info + /json/state in one go
**Notes:** Removes the "add device, click refresh, then drag" friction.

## Identity & continuity

### Q1 — What is the stable identity for a WLED segment in HPC?

| Option | Description | Selected |
|--------|-------------|----------|
| Composite (device_id, seg_index) | Matches WLED's own addressing. User-driven reorder = deliberate reconfig. | ✓ |
| Composite (device_id, seg_name) | Use WLED 'n' as identity. Survives reordering, breaks on empty 'n'. | |
| HPC-owned UUID + reconcile heuristic | Match by name first, range overlap second. Most complex. | |

**User's choice:** Composite (device_id, seg_index)
**Notes:** Predictable, explicit. Reordering on the WLED side is treated as user intent.

### Q2 — When a previously-assigned segment disappears on refresh, what happens to the assignment row?

| Option | Description | Selected |
|--------|-------------|----------|
| Hard-delete the assignment immediately | Drop in same transaction as cache write. | ✓ |
| Keep assignment, mark 'orphan', hide in UI | Preserve intent across temporary edits. | |
| Keep assignment, surface 'broken' badge | Visible to user; explicit clear required. | |

**User's choice:** Hard-delete the assignment immediately
**Notes:** No zombie data; matches the "WLED is source of truth" model.

### Q3 — When a refresh changes a segment's range (same index), what happens?

| Option | Description | Selected |
|--------|-------------|----------|
| Silently update cached range, keep assignment | Frame loop picks up the new range automatically. | ✓ |
| Show 'segment moved' toast, no other action | Same effect plus a one-shot toast. | |
| Treat as a different segment, drop assignment | Conservative; too aggressive given seg_index is the identity. | |

**User's choice:** Silently update cached range, keep assignment
**Notes:** Strip visually re-rendering with the new range is the notification.

### Q4 — Should orientation rows survive when the segments they were assigned to disappear?

| Option | Description | Selected |
|--------|-------------|----------|
| Cascade with the assignment delete | Orientation lives on assignment row; cascade is automatic. | ✓ |
| Preserve orientation in a separate scope | Promote to per-region table independent of assignments. | |

**User's choice:** Cascade with the assignment delete
**Notes:** No separate orientation table needed; orientation has no meaning without an assignment.

## Schema & migration

### Q1 — What's the fate of the wled_channels table?

| Option | Description | Selected |
|--------|-------------|----------|
| Drop wled_channels; re-key wled_light_assignments at (device_id, seg_index) | Clean break. | ✓ |
| Keep wled_channels as a cache table, populated by sync (composite key) | Repurpose with composite PK. | |
| Keep wled_channels schema unchanged; populate from segs | Maximum backward-compat, max complexity. | |

**User's choice:** Drop wled_channels; re-key wled_light_assignments at (device_id, seg_index)
**Notes:** Smallest persistent surface; simplest reasoning model.

### Q2 — Where do segs live at runtime for the coordinator to use?

| Option | Description | Selected |
|--------|-------------|----------|
| In-memory cache on app.state | WledSegmentCache dict on app.state; coordinator reads from memory. | |
| Snapshot to a new wled_seg_cache table on every refresh | Persists to disk; coordinator JOINs it; survives restart. | ✓ (user free-text: "cache them in the db") |
| Re-fetch /json/state from device on every streaming start | No cache; pull fresh each stream. | |

**User's choice:** Snapshot to a new wled_seg_cache table (user typed "cache them in the db")
**Notes:** Survives restart without needing live device contact. Matches Phase 19 D-22 join model.

### Q3 — On refresh, how does wled_seg_cache reconcile against the prior snapshot?

| Option | Description | Selected |
|--------|-------------|----------|
| DELETE all rows for device + INSERT new seg[] in one tx | Cache mirrors device exactly. | ✓ |
| UPSERT per seg + DELETE rows with index >= new count | Targeted updates. | |

**User's choice:** DELETE all rows + INSERT in one tx
**Notes:** Simplest; orphan-assignment cascade falls out of the join naturally.

### Q4 — Upgrade path from Phase 19's wled_channels?

| Option | Description | Selected |
|--------|-------------|----------|
| Drop wled_channels + wled_light_assignments, recreate fresh | Single-user tool; no production data to preserve. | ✓ |
| Migrate by best-effort range match | On first init, hit each device and rewrite assignment rows. | |
| Migrate by truncating only assignments | Halfway; confusing for future readers. | |

**User's choice:** Drop both tables, recreate fresh
**Notes:** Re-registering devices + re-assigning regions is the accepted upgrade cost.

### Q5 — How should the 4 deferred manual UATs (V1–V4) be re-mapped?

| Option | Description | Selected |
|--------|-------------|----------|
| All 4 re-mapped, executed once before phase close | V3 obsolete and replaced with refresh roundtrip test. | ✓ |
| Only V1 + V4; drop V2/V3 as architecture changed | Minimum hardware-touching set. | |
| Skip manual UATs, defer to later hardening pass | Risk: deferred items pile up. | |

**User's choice:** All 4 re-mapped, executed once before phase close
**Notes:** V1/V2/V4 preserve intent; V3 replaced with "edit seg on WLED app → click HPC refresh → verify strip re-renders".
