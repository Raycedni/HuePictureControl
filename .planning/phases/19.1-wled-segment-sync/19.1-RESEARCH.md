## Summary

This phase replaces Phase 19's user-painted `wled_channels` table with a refresh-driven mirror of WLED's own `seg[]` array. Most architectural questions are locked in CONTEXT.md (D-01..D-23). Remaining research gaps fall into four buckets: **WLED API exact semantics** (especially the `stop` inclusive-vs-exclusive trap), **defensive parsing** for `fetch_wled_state`, **SQLite upgrade guard mechanism**, and a **dead-reference map** for safe deletes.

**Primary recommendations:**

1. **`stop` is EXCLUSIVE on the WLED wire** — convert to inclusive `stop_led = seg.stop - 1` at parse time before any DB write. This is the most important translation in the phase and easy to miss because Phase 19's `end_led` column is inclusive.
2. **Pre-parse the device response OUTSIDE the transaction; reconcile INSIDE.** Network I/O has no place in a SQLite transaction. Failure modes get cleaner and the partial-wipe risk disappears.
3. **Use `PRAGMA user_version` for the one-shot Phase 19 → 19.1 upgrade guard.** Simplest, atomic, survives across restarts, matches the existing one-line idempotent ALTER pattern in `init_db`.
4. **`seg.id` is unreliable as positional source-of-truth on firmware 0.14.0-b1** (issue #3041); use the **array index** as `seg_index` and ignore the `id` field. CONTEXT.md D-11 already says this; research confirms it.
5. **`fetch_wled_state` mirrors `fetch_wled_info` exactly** — same 5s default timeout, same exception classes, same defensive `data.get(...)` parsing. One additional concern: WLED returns `state.seg`, not `seg` at root.
6. **Test strategy for the new model:** stand up a tiny `httpx.MockTransport` for unit tests of `fetch_wled_state`; mock the new `/api/wled/devices/{id}/segments/refresh` endpoint at `fetch` layer for Vitest; rewrite `e2e/wled-paint.spec.ts` as `e2e/wled-segments.spec.ts` with a "segment list renders from refresh response" smoke test using `page.route()` to stub the WLED device.
7. **Dead-reference map (Section 7):** 17 files reference deletion targets. The planner can confidently sequence deletes in a wave after all replacements land.
8. **No notable firmware variance issues for `/json/state` GET** on stable 0.13.x/0.14.x/0.15.x — the known 0.14.0-b1 segment-id breakage only affects POST/PUT, not GET. Defensive parsing covers it anyway.

### `seg[]` field map — Phase 19.1 relevance

|-------|------|----------------------------|-----------------|-----------|
| `id` | int | Often, but **NOT GUARANTEED** — docs say "may be omitted, in that case the ID will be inferred from the order" | **IGNORE.** Use array index as `seg_index` (D-11) | HIGH (kno.wled.ge + #3041) |
| `start` | int | Yes when segment is active | `cache.start_led = seg["start"]` | HIGH |

| `len` | int | Present in responses but documented as redundant: `len == stop - start`. Read-only since v0.8.4 | Optional; if used, `cache.stop_led = seg["start"] + seg["len"] - 1` | HIGH |

### Critical behavioral facts

1. **`stop` is EXCLUSIVE.** Documented verbatim at https://kno.wled.ge/features/segments/ — "The Stop LED is **not** included in the Segment." Phase 19's `wled_channels.end_led` was **inclusive**. Conversion: `stop_led = seg["stop"] - 1`.
   - Concrete example: a 30-LED strip with one segment covering all LEDs has `seg.start=0, seg.stop=30, seg.len=30`. HPC cache stores `start_led=0, stop_led=29`. `N_region = stop_led - start_led + 1 = 30`. Phase 19's gradient contract continues to work because the math (D-22: `max(stop_led - start_led + 1)`) is inclusive-on-both-ends.

2. **Disabled / deleted segments are OMITTED from the response array.** A segment whose `stop ≤ start` is "invalidated and deleted" by WLED; the response omits it. So `seg[]` only contains active segments. There is no "disabled flag" to check. [VERIFIED: kno.wled.ge]

3. **`id` field is unreliable.** On firmware 0.14.0-b1, creating a segment with id=9 makes WLED show "Segment 1" in the UI (issue #3041). The official docs also say `id` "may be omitted". **CONTEXT.md D-11 already mandates using array order**; this research confirms that is the correct call.

4. **Segment 0 always exists?** Documentation implies yes — segment 0 is the "main segment" with special properties. But:
   - **Defensive note:** if a user has deleted segment 0 via the WLED app, post-restart WLED may return `seg[]` starting at a non-zero `id`. Since CONTEXT.md D-11 uses array index (not the `id` field) we are immune to this — the first array element becomes `seg_index=0` regardless of its WLED-side `id`.
   - **Empty array:** docs do not explicitly guarantee `seg[]` is non-empty. Defensive parsing must handle `state.seg == []` and `state.seg` missing. See § Defensive Parsing.

5. **`seg` can be returned as an object OR an array.** Per `/json/state` docs: "The API accepts both a single object and an array. Example: `{"seg":[...]}` or `{"seg":{...}}`." For **responses** (GET) it's almost always an array, but to be safe `fetch_wled_state` should normalize: if `isinstance(seg, dict): seg = [seg]`.

6. **Max segment count:** 11 (segment 0 + up to 10 user segments, per kno.wled.ge/features/segments/). Phase 19's strip painter limited to 10 channels via paint mechanics; no enforcement needed in 19.1 because we mirror what WLED sends.

### Mapping table — WLED wire format → `wled_seg_cache` row

```python
# Inside fetch_wled_state (services/wled_client.py)
for seg_index, seg in enumerate(state.get("seg", [])):
    if not isinstance(seg, dict):
        continue  # defensive
    start = seg.get("start")
    stop = seg.get("stop")
    if start is None or stop is None:
        continue  # malformed segment — skip
    if stop <= start:
        continue  # WLED says deleted; should not be in response but defensive
    yield {
        "seg_index": seg_index,         # array order — NOT seg.id (D-11)
        "start_led": int(start),
        "stop_led": int(stop) - 1,      # EXCLUSIVE → INCLUSIVE (CRITICAL)
        "name": seg.get("n"),           # may be None
    }
```

## Defensive Parsing for `fetch_wled_state`

### Recommended signature

```python
# Backend/services/wled_client.py — add this sibling to fetch_wled_info

async def fetch_wled_state(ip: str, timeout: float = 5.0) -> list[dict]:
    """GET ``http://{ip}/json/state`` and return a normalized seg[] list.

    Each element: ``{"seg_index": int, "start_led": int, "stop_led": int, "name": str | None}``.
    ``stop_led`` is INCLUSIVE (converted from WLED's exclusive ``seg.stop``).

    Defensive parse: missing or malformed segments are skipped. Empty seg[]
    returns ``[]``. Caller (refresh handler in routers/wled.py) decides whether
    that should propagate or trigger a warning.

    Raises:
        httpx.HTTPStatusError:  device returned a non-2xx response.
        httpx.ConnectError:     device unreachable.
        httpx.TimeoutException: device did not respond within ``timeout`` seconds.
        ValueError:             response body is not parseable JSON or ``state`` key is missing.
    """
    url = f"http://{ip}/json/state"
    async with httpx.AsyncClient(timeout=timeout) as client:
        resp = await client.get(url)
        resp.raise_for_status()
        try:
            data = resp.json()
        except ValueError as exc:
            raise ValueError(f"WLED /json/state returned non-JSON body: {exc}")
    if not isinstance(data, dict):
        raise ValueError(f"WLED /json/state returned non-dict body: {type(data).__name__}")
    seg_raw = data.get("seg")
    if seg_raw is None:
        # Some firmwares might nest state.seg; try that too.
        state = data.get("state")
        if isinstance(state, dict):
            seg_raw = state.get("seg")
    if seg_raw is None:
        return []  # no segments key at all — defensive empty
    # Normalize: WLED may return seg as object or array (per JSON API docs).
    if isinstance(seg_raw, dict):
        seg_raw = [seg_raw]
    if not isinstance(seg_raw, list):
        raise ValueError(f"seg field has unexpected type: {type(seg_raw).__name__}")

    out: list[dict] = []
    for seg_index, seg in enumerate(seg_raw):
        if not isinstance(seg, dict):
            logger.warning("WLED %s seg[%d] is not a dict, skipping", ip, seg_index)
            continue
        start = seg.get("start")
        stop = seg.get("stop")
        if start is None or stop is None:
            # Try len as fallback (per docs: len = stop - start)
            seg_len = seg.get("len")
            if start is not None and seg_len is not None:
                stop = int(start) + int(seg_len)
            else:
                logger.warning(
                    "WLED %s seg[%d] missing start/stop/len, skipping", ip, seg_index
                )
                continue
        try:
            start_int = int(start)
            stop_int = int(stop)
        except (TypeError, ValueError):
            logger.warning("WLED %s seg[%d] start/stop not int-coercible", ip, seg_index)
            continue
        if stop_int <= start_int:
            # Per WLED docs: this means the segment is invalidated/deleted.
            # Should not appear in response, but defensive.
            continue
        name = seg.get("n")
        out.append({
            "seg_index": seg_index,
            "start_led": start_int,
            "stop_led": stop_int - 1,    # EXCLUSIVE → INCLUSIVE
            "name": name if isinstance(name, str) else None,
        })
    return out
```

## SQLite Upgrade Guard

### Recommendation: use `PRAGMA user_version`

**Why:**
- Single-statement read on startup, single-statement write after migration.
- Persists in the database file (survives restart and migration).
- Atomic with the migration transaction — bump only when migration succeeds.
- Cleanest mental model: each future schema change increments user_version by 1.
- Matches the existing `init_db` style (one short defensive try/except per change).
- No new table to maintain.

**Caveat (cited):** `PRAGMA user_version` is **not included in `sqlite3 .dump` output**, so a dump+restore loses it. Acceptable for this project — HuePictureControl single-machine deployment never round-trips through SQL dumps.

### Pattern (drop-in for `database.py`)

```python
# Backend/database.py — add this block to init_db() after the existing
# Phase 19 idempotent ALTER blocks, before final db.commit()

# Phase 19.1: drop+recreate upgrade from Phase 19 paint-managed wled_channels
# to refresh-mirrored wled_seg_cache. One-shot — gated by user_version.
PHASE_19_1_USER_VERSION = 1

async with db.execute("PRAGMA user_version") as cur:
    version_row = await cur.fetchone()
current_version = int(version_row[0]) if version_row else 0

if current_version < PHASE_19_1_USER_VERSION:
    # Drop Phase 19 tables (D-20). DROP TABLE IF EXISTS is idempotent on its own
    # but the version gate guarantees we don't drop a freshly-created table on
    # subsequent restarts.
    await db.execute("DROP TABLE IF EXISTS wled_channels")
    await db.execute("DROP TABLE IF EXISTS wled_light_assignments")
    # Recreate wled_light_assignments with new shape (D-13).
    await db.execute("""
        CREATE TABLE wled_light_assignments (
            region_id TEXT NOT NULL,
            wled_device_id TEXT NOT NULL,
            seg_index INTEGER NOT NULL,
            entertainment_config_id TEXT NOT NULL,
            orientation TEXT NOT NULL DEFAULT 'auto',
            PRIMARY KEY (region_id, wled_device_id, seg_index, entertainment_config_id)
        )
    """)
    # Create the new cache table (D-12).
    await db.execute("""
        CREATE TABLE wled_seg_cache (
            device_id TEXT NOT NULL,
            seg_index INTEGER NOT NULL,
            start_led INTEGER NOT NULL,
            stop_led INTEGER NOT NULL,
            name TEXT,
            refreshed_at TEXT NOT NULL,
            PRIMARY KEY (device_id, seg_index),
            FOREIGN KEY (device_id) REFERENCES wled_devices(id) ON DELETE CASCADE
        )
    """)
    # Bump user_version — done last so a mid-migration failure does NOT mark
    # the upgrade complete and the guard fires again on next boot.
    await db.execute(f"PRAGMA user_version = {PHASE_19_1_USER_VERSION}")
    await db.commit()
else:
    # Already migrated — but still ensure tables exist (fresh-install or test
    # databases that were created at user_version=1 directly).
    await db.execute("""
        CREATE TABLE IF NOT EXISTS wled_light_assignments (
            region_id TEXT NOT NULL,
            wled_device_id TEXT NOT NULL,
            seg_index INTEGER NOT NULL,
            entertainment_config_id TEXT NOT NULL,
            orientation TEXT NOT NULL DEFAULT 'auto',
            PRIMARY KEY (region_id, wled_device_id, seg_index, entertainment_config_id)
        )
    """)
    await db.execute("""
        CREATE TABLE IF NOT EXISTS wled_seg_cache (
            device_id TEXT NOT NULL,
            seg_index INTEGER NOT NULL,
            start_led INTEGER NOT NULL,
            stop_led INTEGER NOT NULL,
            name TEXT,
            refreshed_at TEXT NOT NULL,
            PRIMARY KEY (device_id, seg_index),
            FOREIGN KEY (device_id) REFERENCES wled_devices(id) ON DELETE CASCADE
        )
    """)
```

### Critical ordering note

The existing `init_db` in `database.py` (lines 97-126) creates `wled_devices`, `wled_channels`, `wled_light_assignments` in that order with `CREATE TABLE IF NOT EXISTS`. After Phase 19.1:

- `wled_channels` `CREATE TABLE IF NOT EXISTS` MUST be removed (otherwise it'd re-create the dropped table on next startup).

## Reconciliation Transaction

### Correctness review of CONTEXT.md `<specifics>` pseudocode

The pseudocode given in CONTEXT.md `<specifics>` (lines 199-217) has three subtle issues against aiosqlite reality:

1. **`async with db.transaction():`** — aiosqlite doesn't expose a `.transaction()` context manager. Use the existing project pattern: implicit transaction, explicit `db.commit()`, try/except with `db.rollback()`. This is the same pattern used in `Backend/services/wled_channels.py` lines 178-215 today.
2. **`cursor.rowcount`** — works on aiosqlite cursors, but cursor must be awaited (`cursor = await db.execute(...)`) and `rowcount` is plain attribute (not coroutine). Confirmed in `Backend/routers/wled.py:792-798` (the `patch_region_orientation` endpoint already uses this exact idiom).
3. **Fetch placement** — the pseudocode wraps the device fetch implicitly outside the transaction (the `rows` variable is referenced from the executemany inside the transaction, implying it was parsed earlier). Make this explicit. Network I/O has no place in a SQLite transaction:
   - Holds a write lock while waiting on httpx (blocks other writers including the coordinator's enabled-toggle path)
   - If the device fetch raises after the cache DELETE has run, we lose all cache rows on a transient network blip

### Recommended structure (fetch outside, transact inside)

```python
# Inside the new Backend/services/wled_segments.py
# (sibling to wled_channels.py, same module-level pattern)

from datetime import datetime, timezone

async def reconcile_segments(
    db: aiosqlite.Connection,
    device_id: str,
    segments: list[dict],   # PRE-PARSED by fetch_wled_state — no network I/O here
) -> int:
    """Replace wled_seg_cache for device_id with segments[], cascade orphan
    assignments. Returns count of dropped assignments.

    SINGLE TRANSACTION. Caller (the refresh endpoint) MUST have already called
    fetch_wled_state and translated any httpx/ValueError to an HTTPException
    BEFORE invoking this.
    """
    now_iso = datetime.now(timezone.utc).isoformat()
    try:
        # 1. Wipe cache for this device (D-19).
        await db.execute(
            "DELETE FROM wled_seg_cache WHERE device_id = ?", (device_id,)
        )
        # 2. Insert new rows. Use executemany for batch speed (small N though).
        await db.executemany(
            "INSERT INTO wled_seg_cache "
            "(device_id, seg_index, start_led, stop_led, name, refreshed_at) "
            "VALUES (?, ?, ?, ?, ?, ?)",
            [
                (device_id, s["seg_index"], s["start_led"], s["stop_led"],
                 s.get("name"), now_iso)
                for s in segments
            ],
        )
        # 3. Cascade orphan assignment deletes (D-15). NOT IN subquery on the
        #    same table works fine in SQLite.
        cur = await db.execute(
            "DELETE FROM wled_light_assignments "
            "WHERE wled_device_id = ? AND seg_index NOT IN ("
            "    SELECT seg_index FROM wled_seg_cache WHERE device_id = ?"
            ")",
            (device_id, device_id),
        )
        dropped = cur.rowcount or 0
        await db.commit()
        return dropped
    except Exception:
        await db.rollback()
        raise
```

### Failure modes catalogued

| Failure point | What happens | Recovery |
|---------------|-------------|----------|
| `fetch_wled_state` raises `TimeoutException` | Router catches, returns 502, no DB writes | Frontend falls back to GET /segments (D-04) |
| `fetch_wled_state` raises `ValueError` (malformed response) | Router catches, returns 422, no DB writes | User sees error toast; cache untouched |
| All segments parsed but `segments == []` (device cleared all segs) | Cache wiped, all assignments cascade-deleted, returns dropped count | Strip renders empty in UI; correct per D-15 |
| `executemany` fails mid-batch (e.g. UNIQUE violation on PK) | Rollback fires; cache reverts to pre-DELETE state | Should not happen — PK is composite `(device_id, seg_index)` and seg_index is unique by array index. Defensive only. |
| Power loss between DELETE and INSERT | SQLite WAL rolls back the uncommitted transaction on next open | Cache unchanged from before this refresh attempt |
| Concurrent refresh of the same device | aiosqlite serializes per-connection; second refresh waits | Second call sees first's results (cache + assignments) — idempotent in result, not in side-effect timing |

### Why NOT wrap the fetch in the transaction

- **Network latency holds the write lock for up to `timeout=5.0`s.** The coordinator's `set_wled_device_enabled` runs `UPDATE wled_devices SET enabled = ?` — that write would queue behind a hung refresh. Even worse, the frame loop's `_load_wled_device_rows` SELECTs run on the same connection and would compete with the held write lock.
- **Partial wipe risk** — if the DELETE succeeds and then the device disconnects mid-response read, the rollback after the failed parse would have to roll back DELETE work that may already have flushed pages (in WAL mode SQLite handles this correctly via the WAL, but it's wasted work).
- **Error reporting** — the parser raising on a bad response should bubble up as 422; that's awkward when the txn is in flight (need to translate exception types twice).

### Pattern parallel to existing code

This structure mirrors `Backend/services/wled_channels.py`:`create_channel_with_split` (lines 74-223):

1. Validate inputs (here: handled by `fetch_wled_state` defensive parse)
2. Pre-compute work (here: build `segments` list from device response)
3. Enter try/except, run statements, `await db.commit()`, return result
4. On exception: `await db.rollback()`, re-raise

### Wave-sequencing recommendation

Three sensible orderings exist; the planner should pick one and stick to it:

1. **"Backend-first" (recommended):** Wave 0 fixtures + Wave 1 schema + Wave 2 backend service/router + Wave 3 backend tests + Wave 4 frontend rewrites + Wave 5 deletes-only wave + Wave 6 e2e.
2. **"Vertical slice":** Each wave touches one feature area (segment list, refresh, assignment, orientation) backend+frontend together. Higher merge-conflict risk.
3. **"Big-bang":** All deletes + all rewrites in one wave. Smallest total churn, highest blast radius. Not recommended for a code base with active CI.

The dead-reference map above is structured to support option 1.

## Common Pitfalls

### Pitfall 1: `stop` inclusive/exclusive mismatch
**What goes wrong:** Storing `stop_led = seg["stop"]` directly. Every segment's range is off by one — last LED is dark.
**Why it happens:** Phase 19's `wled_channels.end_led` was inclusive; WLED's `seg.stop` is exclusive. The naming sounds similar.
**How to avoid:** Convert at the parse boundary — `stop_led = seg["stop"] - 1`. Document the convention loudly in the `fetch_wled_state` docstring and the `wled_seg_cache` CREATE TABLE comment.
**Warning signs:** Off-by-one bugs in LED color during V1; strip ends one LED short on the right.

### Pitfall 2: Network I/O inside DB transaction
**What goes wrong:** Refresh that wraps `await fetch_wled_state` inside `try / commit / except / rollback`. Slow device hangs the write lock; concurrent enabled-toggles or coordinator reads queue.
**Why it happens:** Pseudocode in CONTEXT.md `<specifics>` reads as if everything is in one txn.
**How to avoid:** Two-step: (1) `segments = await fetch_wled_state(ip)` — raises httpx errors freely; (2) `dropped = await reconcile_segments(db, device_id, segments)` — pure DB work inside txn.
**Warning signs:** Frame loop drops to 1-2 fps during a hung refresh; test `test_reconcile_atomic_no_intermediate_state` flakes under concurrency.

### Pitfall 3: Upgrade guard fires more than once
**What goes wrong:** Using a presence-check on `wled_seg_cache` as the guard. On the first restart after the migration runs, the cache is empty (no device refreshed yet) — the planner could mistakenly re-fire the drop.
**Why it happens:** "Empty cache" looks the same as "Phase 19 schema, no migration yet."
**How to avoid:** Use `PRAGMA user_version`. Bump it ONLY after all DDL succeeds.
**Warning signs:** Devices vanish after a restart that should have been a no-op; tests for idempotent init fail intermittently.

### Pitfall 4: Confusing `seg.id` with array index
**What goes wrong:** Code reads `seg["id"]` as the `seg_index`. On firmware 0.14.0-b1 (and any firmware where the user deleted segment 0 and recreated it), the id may not match position.
**Why it happens:** WLED docs are unclear; `seg.id` looks like the canonical identifier.
**How to avoid:** Always use `enumerate(seg_raw)` index. CONTEXT.md D-11 already mandates this; tests should explicitly cover the case where `seg.id != array_index` (see Defensive Parsing test table).
**Warning signs:** Strip painter renders zones at wrong positions on certain firmwares; tests with `id=9` payloads fail.

### Pitfall 5: Forgetting to update `Backend/tests/test_phase17_e2e.py` fixture schema
**What goes wrong:** The Phase 17 e2e test creates its own `wled_light_assignments` schema inline (lines 86-92 of `test_phase17_e2e.py`). If only `Backend/database.py` is updated, those tests still use the old schema and pass against the wrong table layout.
**Why it happens:** Tests with inline schema fixtures don't pick up `database.py` changes.
**How to avoid:** Update the fixture in `test_phase17_e2e.py` alongside the `database.py` change (Wave 1).
**Warning signs:** Phase 17 e2e tests pass locally but blow up against `database.py`-managed schema in CI.

### Pitfall 6: SettingsPanel mounting both old and new sidebar
**What goes wrong:** `SettingsPanel.tsx` (line 8, 51) and `SettingsPage.tsx` (line 14, 35) both mount `WledChannelSidebar`. If only one is updated, the other surface still shows the old paint UI.
**Why it happens:** Two-surface mount pattern (CONTEXT.md "Both surfaces share the same component").
**How to avoid:** Grep for `<WledChannelSidebar` and update both call sites in the same diff.
**Warning signs:** UI looks correct in the drawer but wrong in the page (or vice versa).

## Code Examples

### Refresh endpoint structure

```python
# Backend/routers/wled.py — add to existing file

class WledSegmentOut(BaseModel):
    seg_index: int
    start_led: int
    stop_led: int
    name: str | None = None

class WledSegmentsResponse(BaseModel):
    segments: list[WledSegmentOut]

class WledRefreshResponse(BaseModel):
    segments: list[WledSegmentOut]
    dropped_assignments: int

@router.post(
    "/devices/{device_id}/segments/refresh",
    response_model=WledRefreshResponse,
)
async def refresh_segments(device_id: str, request: Request) -> WledRefreshResponse:
    """Fetch /json/state from the device and reconcile wled_seg_cache (D-17)."""
    db = request.app.state.db
    async with db.execute(
        "SELECT id, ip FROM wled_devices WHERE id = ?", (device_id,)
    ) as cur:
        row = await cur.fetchone()
    if row is None:
        raise HTTPException(404, detail=f"WLED device '{device_id}' not found")
    # Fetch OUTSIDE the transaction.
    try:
        segments = await fetch_wled_state(row["ip"])
    except httpx.TimeoutException as exc:
        raise HTTPException(502, detail=f"WLED device unreachable (timeout): {exc}")
    except httpx.ConnectError as exc:
        raise HTTPException(502, detail=f"WLED device unreachable: {exc}")
    except httpx.HTTPError as exc:
        raise HTTPException(502, detail=f"WLED device returned error: {exc}")
    except ValueError as exc:
        raise HTTPException(422, detail=f"Invalid WLED response: {exc}")
    # Reconcile INSIDE the transaction.
    dropped = await reconcile_segments(db, device_id, segments)
    return WledRefreshResponse(
        segments=[WledSegmentOut(**s) for s in segments],
        dropped_assignments=dropped,
    )
```

# Backend/services/streaming_coordinator.py — _build_region_plan rewrite

sql = """
    SELECT DISTINCT r.id AS region_id, r.polygon,
           COALESCE(MAX(wsc.stop_led - wsc.start_led + 1), 1) AS n_region,
           COALESCE(MAX(wla.orientation), 'auto') AS orientation
    FROM regions r
    LEFT JOIN light_assignments la
        ON la.region_id = r.id AND la.entertainment_config_id = :cfg
    LEFT JOIN wled_light_assignments wla
        ON wla.region_id = r.id AND wla.entertainment_config_id = :cfg

        ON wsc.device_id = wla.wled_device_id
       AND wsc.seg_index = wla.seg_index
    WHERE la.region_id IS NOT NULL OR wla.region_id IS NOT NULL
    GROUP BY r.id, r.polygon
"""

## Open Questions

1. **Should `WledStreamer` accept `seg_index` directly or keep its existing `channel.id` field shape?**
   - What we know: `WledStreamer.start(device_rows)` currently expects `channels: [{id, region_id, start_led, end_led}]`.
   - What's unclear: cleanest API surface — keep `id` field but pass `str(seg_index)`, or rename to `seg_index` and update WledStreamer too.
   - Recommendation: minimal-diff path is keep `id` field on the coordinator-to-streamer contract, populate it with `seg_index` as a string. Defer the rename to a future cleanup unless the planner sees a clean reason to refactor `WledStreamer` here.

2. **Should the refresh endpoint return the FULL device row (with updated cache) or just the segments + dropped count?**
   - What we know: CONTEXT.md D-17 says "returns the post-refresh segment list + the count of assignments dropped".
   - What's unclear: whether to also return the device row's `connected`/`last_success_at` to refresh the device-row UI in one shot.
   - Recommendation: keep response narrow per D-17. Frontend can re-fetch `GET /api/wled/devices` if it needs the updated header. Simplicity wins.

3. **Where does the per-device "stale" age threshold live — frontend constant or backend response?**
   - What we know: CONTEXT.md says ~60s feels right (Claude's discretion).
   - What's unclear: whether the response should include a `stale_seconds` recommendation or the frontend hardcodes 60.
   - Recommendation: frontend constant. Backend ships ISO timestamp only; UI does the comparison.

4. **Should the device registration flow REQUIRE `fetch_wled_state` to succeed, or treat it as a soft prerequisite?**
   - What we know: CONTEXT.md D-02 says "both calls in the same coroutine, so registration fails atomically if either fails".
   - What's unclear: what happens if `/json/info` succeeds but `/json/state` returns empty `seg[]` (no segments configured).
   - Recommendation: empty `seg[]` is valid (device is online, no user segments). Registration succeeds with zero rows in `wled_seg_cache`. User clicks Refresh later after configuring segments WLED-side. The 502 (unreachable) case during registration should fail registration atomically per D-02; the empty case should not.
