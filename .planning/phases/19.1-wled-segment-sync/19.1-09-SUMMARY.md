## Decisions Made

### V3' stays manual UAT, not Playwright

The full V3' roundtrip (configure two adjacent segments on the WLED app, change the boundary on the device side, click HPC Refresh, see the strip re-render with new ranges) needs a real device responding to two distinct `/json/state` payloads. `page.route()` can stub a static response, but the "refresh sees a different shape than the cache" semantics require either a stateful in-memory mock or a live WLED. The CONTEXT.md D-23 mapping flags V3' as manual UAT for exactly this reason. The new `segments render from refresh response (stubbed)` spec covers the stubbable subset — clicking the button surfaces three segments — which is the meaningful Playwright-testable surface.

### Drag-payload capture via synthetic dispatchEvent, not page.dragAndDrop

Playwright's native `page.dragAndDrop` requires a real drop target receiving the drag and completing a drop. The assertion in spec #3 is about the `dataTransfer.setData()` calls on the source side, not about whether the drop succeeded. Synthetic `dispatchEvent` with a fake DataTransfer that records every setData call pins the contract directly without coupling to EditorCanvas drop-target geometry or hit-testing. This mirrors the same pattern used in `LightPanel.test.tsx` (Plan 08), so future maintainers see consistent harness shapes between unit + e2e tests.

### Negative-assertion preservation

Both `LightPanel.test.tsx` (line 437, 453) and the new `wled-segments.spec.ts` (line 278, 279) keep negative assertions that Phase 19 legacy keys (`wledChannelId`, `wled_channel_id`) are NOT in the drag payload. These cost nothing to maintain and guard against a future re-introduction of the Phase 19 payload shape that would silently break the EditorCanvas drop-target discriminator (which now branches on `wledDeviceId` presence). Same posture as `test_database.py`'s `assert "wled_channels" not in names` — bricks placed against the path of regression.

### Single-page navigation in the new spec

The app uses state-driven page switching (`Frontend/src/App.tsx` line 11: `useState<Page>`) rather than React Router. The old `wled-paint.spec.ts` navigated via `page.goto('/')` and assumed the Settings strip was visible on the home page, which is wrong — the Settings tab is only mounted when `page === 'settings'`. New helper `openSettingsTab` does `page.goto('/')` + click the Settings nav button + wait for `wled-strip-painter` to be visible. The drag-payload spec uses the same pattern with `Editor` instead.

### `paint` and `boundary` words avoided in the new spec

The plan's acceptance criterion *"`grep -c 'paint\b\|boundary\b' Frontend/e2e/wled-segments.spec.ts` returns `0`"* was strictly enforced. The initial JSDoc header used both words contextually ("replaces wled-paint.spec.ts (paint-creates-channel + boundary drag)"), then was rewritten to read *"Replaces the legacy Phase 19 e2e suite..."* with V3' described as "refresh after a WLED-side range change" instead of "boundary change". Functional intent unchanged, vocab parity preserved.

## Deviations from Plan

### None — plan executed exactly as written

Both tasks completed against the plan's action steps and acceptance criteria. The two minor refinements during execution:

1. **Spec #1's segment-listing assertion uses `toBeAttached()` instead of `toBeVisible()`** — the ZoneTestSentinel hidden span (`display:none, aria-hidden`) is in the DOM but not visible, so `toBeVisible()` would fail. `toBeAttached()` is the correct Playwright matcher for invisible-but-present DOM nodes. Same semantic guarantee (segments rendered → testid exists).

2. **`openSettingsTab` helper added rather than direct `page.goto('/settings/wled')`** — the plan body's example used a URL-routed path, but the app is single-page state-driven. The helper does the same thing the user would do (click the Settings nav button) and waits for the strip to be visible.

Neither is a Rule 1-3 fix; they're plan-conformant adjustments to match the actual application architecture.
